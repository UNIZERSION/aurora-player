# Aurora screen lock

The optional screen lock uses a four-digit PIN chosen locally on Tab5. There is no default PIN. Every combination from `0000` to `9999` is accepted; leading zeroes are significant. Settings asks for the new PIN twice before enabling or changing it. Changing or disabling an existing PIN requires the current PIN.

When enabled, the device locks when its screen turns off and starts locked after a reboot. Waking the display presents the PIN screen. Enabling the feature while using Settings leaves the current session unlocked until the next screen-off event. Playback can continue in the background while the screen is locked.

Five incorrect attempts start a 30-second cooldown. Unlock, change-PIN, and disable-PIN checks share the same attempt budget. A correct PIN resets that budget; blanking, waking, or reloading the configuration does not. The timer uses monotonic uptime rather than the adjustable clock. The attempt budget and cooldown are held in RAM and reset on reboot.

The enabled state, a fresh 16-byte salt, a SHA-256 digest of `salt || PIN`, and the selected wallpaper basename are stored together in internal-flash NVS. The PIN itself is not stored. Removing the SD card does not disable the lock. NVS load errors or an invalid record leave the controller locked; it never erases NVS as an automatic recovery step. Failed saves leave the active configuration unchanged. A power interruption during an NVS update can recover the complete previous or complete new record.

Version 1.3.14 uses the dedicated `aurora_cfg` NVS region at `0xF10000`, size `0x6000`, isolated from shared NVS. On an upgrade, the existing credential migrates automatically; a migration failure remains locked. Every save commits and reopens the namespace to compare the stored record before acknowledging success. A durable marker in shared NVS prevents fallback to a stale PIN after migration. The marker is committed before changing the private credential and recreated at startup if shared NVS was erased. Normal PIN entry writes no NVS data.

If a later partition table omits `aurora_cfg`, Aurora registers the same fixed region in RAM using ESP-IDF's `esp_partition_register_external` API. This does not rewrite the partition table. The SDK rejects overlap with existing partitions and addresses outside the flash chip. Before any private NVS initialization, a bounded read-only probe checks at most six 4 KiB pages: storage must be entirely erased or contain a written `aurora_lock` namespace entry with valid NVS page and entry CRCs. Unknown nonempty data, read failures, incorrect named-partition metadata, and registration failures leave the interface locked. The namespace probe establishes ownership only; the normal NVS reader and ALK1 decoder still validate the actual credential. An owned region with a missing or corrupt credential never becomes first-run setup. A disabled first-run record is persisted even before choosing a PIN, so this state also survives missing table entries. No extra signature partition is needed.

Complete erasure of both NVS regions remains a factory reset; this is not protection against physical flash modification. A live pre-installation read found a six-MiB Aurora partition where an earlier table had twelve MiB; the reason for this difference and the user's original PIN loss are not proven. Host simulations validate recovery after missing table entries and loss of shared NVS, but cannot establish survival of actual cold power cycles. Physical power-off validation is reported separately when performed.

Custom wallpapers are JPG, JPEG, or PNG files in `/sdcard/Aurora/Lockscreen`. The stored selection is a basename of at most 240 bytes, without directory separators or traversal components. An empty selection uses the frosted player backdrop. The wallpaper is optional and does not contain the PIN configuration.

Wallpaper files are limited to 8 MiB (8,388,608 bytes). The existing TJpgDec decoder supports baseline JPEG within 4096 pixels per edge and 16 Mi pixels total; progressive JPEG and unsupported JPEG sampling layouts return an explicit unsupported-image message. PNG files may contain at most 1 Mi pixels (1,048,576), with at most 8 bits per channel and no edge above 4096 pixels. PNG palette, grayscale, and alpha modes are supported; transparent pixels are composited over a neutral milk tint. A 1280×720 PNG is within the pixel limit. Decoding also requires enough free memory to preserve a 2 MiB PSRAM reserve for playback, so an otherwise valid image can be rejected under memory pressure. The picker returns at most 128 files and scans at most 2048 directory entries.

Custom images are center-cropped to 16:9 and decoded once to a native 1280×720 RGB565 buffer. The default frosted background is deliberately static: the controller captures the main player at 1280×720, downsamples to 320×180, applies three separable blur passes and a neutral milk tint, and prepares one 1280×720 RGB565 image. Both paths composite the dark veil once in the worker, so LVGL displays an opaque image at 1:1 with no full-screen scaling or translucent veil blend. Work runs outside the LVGL lock, with cooperative cancellation and yields during reads, JPEG output, fixed-buffer PNG inflation, and blur loops. It does not blur or decode on every frame. A missing SD card, deleted file, unsupported or corrupt image, or insufficient memory falls back to the cached frosted player view. If no capture is available, the PIN interface remains usable over its solid dark background.

This feature controls access to Aurora's interface. It does not encrypt the SD card, protect files read in another device, or provide a security boundary against modified firmware or direct flash access. Four decimal digits have only 10,000 possible values; the salted verifier is not intended to provide phone-grade protection against an offline attack.

## Verification

`tests/run_screen_lock_tests.ps1` compiles the platform-independent model and the production NVS adapter against SDK test shims. The tests cover PIN setup/change/disable, `0000`, every digest byte, reboot behavior, invalid records and I/O failures, the shared cooldown and exact expiry boundary, regressing or long-running clocks, and wallpaper filename validation. These host fixtures test the storage integration contract; mbedTLS itself supplies SHA-256 in the firmware build. They do not constitute a physical-device test.

The same runner also compiles the real `aurora_lock_controller.inc` against host UI and hardware fixtures. That suite checks setup confirmation, current-PIN authentication, Cancel restrictions, stale command queues, clearing temporary PIN buffers, relocking during a PIN change, delayed UI-lock recovery, missing SD, image-publication retries, and worker ownership during cancellation. It does not emulate the display driver or real task scheduling.

The 1.3.14 tests additionally simulate six fresh controllers after removing the private partition-table entry and clearing shared NVS, automatic migration, failed commit/readback, stale PIN fallback prevention, first-run reboot before selecting a PIN, corrupt page/item CRCs, erased namespace entries, arbitrary nonempty flash, SDK registration refusal, incorrect named-partition metadata, and missing/corrupt credentials after ownership is established. The host SDK shim models overlap/bounds refusal; it does not emulate actual flash operations. PIN typing changes only the affected mask dot rather than resetting styles on all four dots. A busy display is acquired for at most 20 ms per digit; a pending repaint retries without dropping the accepted input. `lock_ui_test.cpp` measures actual LVGL dirty pixels for changed and unchanged PIN views.

`tests/run_lock_wallpaper_tests.ps1` exercises the production wallpaper helper with real TJpgDec and LodePNG decoding. It covers full-screen RGBA PNG, 16 Mi-pixel JPEG, narrow/wide/portrait crops, palette and grayscale modes, a 64 KiB ICC boundary, malformed and oversized files, a PNG inflate bomb, cancellation, short reads and interrupted reads, bounded directory enumeration, and deterministic frosted blur. The final host evidence (result file, source SHA-256 hashes and test log) is not published. These checks do not measure on-device decode latency or simulate concurrent PSRAM pressure.
